# Non-ZK SHA-256 / P-256 benchmark backend

Enable `sha256-ecdsa` to use the signed-message adapter. The external statement
is `(log_compressions, Qx, Qy, r, s)`; the message is a witness. The signature
verifies the standard SHA-256 digest of that message. Valid high-s signatures
are accepted. This backend offers no zero-knowledge guarantee and performs no
IVC or recursive verification.

```rust,ignore
use spartan2::sha256_ecdsa::{Prepared, Proof, Statement};

let prepared = Prepared::setup(r, c)?;
let witness = prepared.generate_witness(&statement, &message)?;
let committed = prepared.commit(witness)?;
let (proof, phases) = prepared.prove(&statement, &committed)?;
let wire = proof.to_bytes()?;
let decoded = Proof::from_bytes(&wire)?;
prepared.verify(&statement, &decoded)?;
```

Here `B=2^r` compressions form each of `K=2^c` SHA circuit instances, followed
by one ECDSA core instance. The message contains `64*(B*K-1)` bytes; the last
compression consumes exactly one standard padding block. Total exponents 3..16
are supported. `Prepared` can be reused across messages and signatures with
the same shape. It retains both prover and verifier keys for the benchmark;
the generic `neutronnova` module exposes separate keys.

## Circuits and application binding

SHA chunks use Bellpepper's constrained SHA compression function. Each chunk
publishes its input state, message blocks and output state as range-constrained
32-bit words. These authenticated auxiliary inputs are carried in the proof
and counted in its encoding. The application verifier checks the standard IV,
all adjacent chunk boundaries, the final padding block, the digest shared with
the core, and the expected key/signature. They are essential verification work.
The auxiliary inputs reveal the message, as allowed by the non-ZK interface.

The core uses P-256's coordinate field, which is the scalar field of
`T256HyraxEngine`. It constrains `[s]R = [z]G + [r]Q` with complete projective
formulas, canonical on-curve affine inputs, nonzero terminal projective
coordinates, and `1 <= r,s < n`. The complete formulas retain their RustCrypto
attribution in `licenses/RustCrypto-MIT`. All 256 digest bits form the integer
scalar `z`; it is not reduced modulo the coordinate field.

For `x(R) mod n = r`, a Boolean quotient selects `x(R)=r` or `x(R)=r+n`.
The second branch additionally requires `r < p-n`, making this an integer
equality without a wrap modulo p. Signature hints are generated by RustCrypto
and independently constrained by the core. Missing witness values can be used
for setup; there are no witness-dependent circuit shapes.

## Public protocol

1. Commit to all K SHA witnesses and the core witness. Bind the public key
   digest, length-prefixed application statement, and ordered instances to
   the transcript before sampling challenges.
2. Form all matrix-vector products. Use a cubic NeutronNova batch sumcheck to
   fold the SHA instances, preserving the nonzero folding residual. Batch
   variables bind least-significant bit first. For `c=0`, use the original
   SHA instance directly with zero target and no folding rounds.
3. Run paired outer sumchecks for the folded SHA relation and core relation.
   Bind both round messages before every common challenge. Their distinct
   terminal triples bind before sampling the matrix-combination scalar.
4. Run paired inner sumchecks with common column challenges. The row/column
   ordering follows the existing most-significant-bit Hyrax MLE convention.
   The verifier evaluates each public matrix and public-input polynomial.
5. Bind both witness evaluation claims, sample a fresh batching scalar, and
   combine the witnesses, commitments and blinds. Send one direct Hyrax
   opening with 2,048 field elements. Verify the opening and compare its
   returned value with the batched evaluation claim.

The verifier checks message dimensions, commitments, sumcheck identities,
matrix terminals and application bindings. Proof decoding is length limited
and rejects trailing bytes. Fresh commitment blinds are used, but direct
opening and public protocol messages do not make a ZK proof.

## Measurement and scope

`generate_witness` synthesizes assignments; `commit` creates all commitments;
`prove` includes matrix products, folding, both sumchecks and opening. No
matrix products are hidden in witness preparation. `Phases` contains
non-overlapping matrix, folding, outer, inner and opening timers. Setup,
witness generation, commitment, proving, codec and full application
verification can therefore be timed separately by a caller.

This is a new non-ZK adaptation of the fork's matrix and Hyrax infrastructure,
not the stock ZK multi-circuit prover or a reproduction of the Vega paper's
published measurements. It does not port every optimized kernel/cache from
that path. Security metadata should identify T256 DLOG, the P-256 coordinate
field, Keccak256 Fiat-Shamir, and direct Hyrax; nominal 128-bit group security
is distinct from F2Z's economic proof-of-work security targets.

Run `cargo test --lib --features sha256-ecdsa` for protocol, codec, application
binding, setup reuse, scalar/digest boundary and exceptional point tests.
